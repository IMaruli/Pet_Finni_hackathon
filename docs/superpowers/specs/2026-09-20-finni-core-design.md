## Intent (что уже согласовано по факту переписки и ТЗ)

Обучающее Android-приложение 7–11 лет: ребёнок сам распределяет **игровые монеты** (нужное / желаемое / отложить), видит следствие на питомце, может исправить ошибку без обнуления прогресса. Взрослый смотрит прогресс за барьером и сбрасывает тестовый профиль. Нет экономики вне игры — навсегда, не только в MVP.

Успех хакатона: живое демо Приложения А на физическом устройстве + минимум контента 2.6 + пакет сдачи.

## Архитектура (рекомендация A)

Четыре единицы с ясными границами:

1. **economy** — чистые функции/типы: кошелёк, план, факт, покупка, копилка, период, настроение, стадия. Без Flutter widgets. Вход: команда (`confirmPlan`, `buy`, `transferToSavings`, …). Выход: новое состояние + список объяснений для UI (короткие строки по id копирайта).
2. **content** — загрузка каталога (items, goals, tasks, copy). Домен не знает файловой системы: получает уже разобранные структуры.
3. **profile_store** — запись/чтение снимка профиля; сброс тестового профиля.
4. **app_ui** — экраны, навигация, демо-кнопка «завершить период».

Зависимости только вниз: UI → store + economy + content. Economy не импортирует UI.

### Поток данных

Онбординг создаёт профиль → начисление стартовых монет (с источником) → ребёнок подтверждает план (сумма корзин ≤ баланс) → действия периода меняют кошелёк и показатели питомца → завершение периода считает факт vs план и может сдвинуть стадию → UI показывает тексты из content по id.

### Ошибки

Нехватка монет, план больше баланса, снятие копилки без второго подтверждения — домен возвращает отказ с кодом, UI не списывает. Падений и тупиков в демо быть не должно.

### Тесты

TDD на economy и на правила контента (задание имеет сцену и исходы). UI — ручной чеклист А плюс золотые пути, когда стек позволит. Не мокать домен ради «зелёного» UI-теста.

## Формулы (черновик домена, уточнить в первом writing-plans)

- Баланс ≥ 0 всегда.
- План: need + want + save ≤ available.
- Покупка need/want только если price ≤ available; пишет факт периода.
- Накопления отдельно от available; снятие — двухшаговое.
- Настроение: обратимые уровни от покрытия need и следования плану; **нет** порчи «по календарю, пока приложение закрыто» как наказания.
- Стадия 1..3: пороги по числу периодов с выполненным need, регулярным save и отклонением факт/план в разумных пределах (конкретные пороги — в плане экономики, без магии в UI).
